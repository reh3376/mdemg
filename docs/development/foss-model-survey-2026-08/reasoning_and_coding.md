## Which reasoning model for ape.reflect + rsic.reflect

Both sites emit **bounded JSON reasoning reports** under APE-PROMPT-BUDGET-001's 3,500-token prompt cap inside an 8K-per-slot KV budget — so the binding constraint is not raw reasoning score, it's *controllable, terse* thinking that doesn't starve the output budget (the exact failure mode that poisoned the old ape.reflect eval rows).

- **Primary: Qwen3.8-27B.** Dense (so the FT-RECURSIVE-00x LoRA loop keeps working on Metal — the non-negotiable), Apache 2.0, 262K context, template-level thinking toggle in the Qwen lineage MDEMG already serves (`--jinja`, enable_thinking kwarg — the 14 non-reasoning sites suppress `<think>` the same way today's model does). Its LiveCodeBench-v6 90.3 / SWE-bench-Pro 61.7 imply the structured-reasoning capability ape.reflect needs. Caveat: 3 days old — gate any adoption on a fresh 16-task UBENCH run with `finish_reason=length` checks.
- **Runner-up: Mistral Small 4** — `reasoning_effort` as a *request parameter* (no think-blob post-processing at all, and the terse-CoT style is measurably output-efficient) is the best per-call-site ergonomics of any 2026 open model. It loses on the two structural axes: ~82 GB resident and MoE (no on-box LoRA retrain).
- **Not recommended:** Qwen3.6-35B-A3B — best thinking-per-active-param, but MDEMG already proved this exact base untrainable on M5 Max Metal.

**Token-cost note:** Qwen-style extended thinking typically adds 2–10× output tokens; at `--ctx-size 32768 --parallel 4` that must be paid from the same 8K slot as the prompt. Any reasoning-mode adoption for the two reflect sites should either cap thinking tokens or move those calls to a dedicated wider-slot server profile.
